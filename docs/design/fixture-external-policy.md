# External Fixture Policy Design

Status: Implemented

## Goal

Allow fixture factories to be generated for struct types whose source cannot be edited,
such as the Params and Row structs generated by sqletch or sqlc from DDL.

Today a fixture type needs a `//datlas:fixture` directive and `fixture:"..."` struct tags.
Neither can be added to generated code: the next regeneration removes them.

This document proposes giving the fixture policy of such types from outside the type.

Neither the directive nor the tags are attached to such types.
The relationship is inverted: the policy lives outside and refers to the type.

Hand-written factory methods also work for such types (see
[Coexistence with Hand-written Factory Methods](#coexistence-with-hand-written-factory-methods)).
An external policy is not required; it removes boilerplate and detects added fields.
Hand-written methods need a generated `Factory` to attach to, which today exists only when
at least one `//datlas:fixture` type exists (see [Skeleton-only generation](#skeleton-only-generation)).

---

# Non-goals

- Generating structs from DDL.
  That belongs to a SQL-first layer (sqletch, sqlc). datlas only consumes the resulting Go types.
- Making sqletch or sqlc aware of datlas (e.g. emitting `fixture` tags).
  The dependency must point from datlas to Go types only.
- Inferring policies from field names (`Email` → `email`, `CreatedAt` → `now`).
  Implicit behavior conflicts with the explicit-field rule below.

---

# Overview

```
sqletch / sqlc                datlas
--------------                ------
schema.sql ──▶ gen.InsertUserParams ──┐
                                      ├──▶ datlas fixture ──▶ zz_fixture_gen.go
               fixture/fixture.yaml ──┘
```

The two tools share nothing but Go types.

# Where the Policy Lives

## Options

| Option | Assessment |
| --- | --- |
| **A. YAML policy file** (chosen) | No dummy Go code, no lint noise. Values reuse the struct tag grammar, so `parseTag`/`validate` apply unchanged. Validated strictly at generation time, like master data. |
| B. Shadow struct (`type userPolicy struct { Email struct{} \`fixture:"email"\` }` plus a directive naming the target) | Tags look familiar, but field types are meaningless, the unused type triggers U1000, and field names are matched as strings anyway. |
| C. New directives not attached to a type (`//datlas:field ...`) | Breaks the loader rule that every directive is attached to a type declaration. |
| D. Let sqletch/sqlc emit `fixture` tags | Reverses the dependency direction. |

## Trade-off of Option A

Type and field names are strings, so IDE renames do not follow them.
This is mitigated by failing generation on any unknown type or field:
`go generate` always detects the drift.

# Format

```yaml
# fixture/fixture.yaml
types:
  - type: github.com/example/app/db/gen.InsertUserParams
    name: User            # factory method name; defaults to the type name
    fields:
      ID: uuid
      Email: email
      Age: int,min=18,max=99
      Bio: sentence,wrap=github.com/moznion/go-optional.Some
      CreatedAt: now
      Note: "-"           # explicitly left at its zero value
```

```go
// fixture/doc.go
package fixture

//go:generate go run github.com/moznion/go-datlas/cmd/datlas fixture -config fixture.yaml ../model
```

- Field values use exactly the struct tag grammar. Nothing new to learn.
- `plural` renames the plural method, like `//datlas:fixture plural=...`.
- The same type may be listed several times under different `name`s (e.g. `User` and `AdminUser`).
  Such a type cannot be the target of `nested`, which could not choose a factory.
- PACKAGES may be omitted when `-config` is given.
- Only the packages matched by PACKAGES are scanned for `//datlas:fixture`.
  Packages loaded only because the policy file refers to them are not.

CLI:

```
datlas fixture [-out DIR] [-pkg NAME] [-config FILE] [PACKAGES...]
```

Without PACKAGES and `-config`, only the `Factory` skeleton is generated
(see [Skeleton-only generation](#skeleton-only-generation)).

# Validation

In addition to the rules for `//datlas:fixture`, generation fails when:

- `type` cannot be resolved, is not a struct, is generic, or is not exported
- a key of `fields` does not exist, or is an unexported field of another package
- **a field the generated package can set is not mentioned in `fields`**
  (unexported fields of another package cannot be set and are exempt)
- an embedded field is given a policy other than `nested` or `-`, as with tags
- a factory method name conflicts with another one (already checked today)
- the YAML is malformed or has unknown keys

## Why every field must be mentioned

For in-source tags, untagged fields keep their zero value.
External types deliberately differ.

With in-source tags, adding a field and tagging it happen in the same place.
With external types they do not: when sqletch regenerates a struct with a new column,
the fixture would silently keep producing a zero value for it.

Requiring every field (with `-` for an explicit zero value) turns that drift into a generation error.
This is the main value of an external policy.

# Wrapper Types (`wrap=`)

## Problem

Generated types rarely use plain scalars for optional values:

- sqletch Params and Rows: nullable columns are `optional.Option[T]` (go-optional),
  `@if-present` parameters are `sqletch.Omittable[T]` (unexported fields; constructor required)
- sqlc: `sql.NullString`, `pgtype.Text`, ...

`classify()` treats all of them as `kindOther` and rejects them.
Without a solution, external policies are unusable for most sqletch types.

## Proposal

A `wrap=<function>` parameter names a constructor applied to the generated value:

```yaml
Bio: sentence,wrap=github.com/moznion/go-optional.Some
Nick: username,wrap=nullString
```

```go
// fixture/wrap.go (hand-written, in the fixture package)
func nullString(s string) sql.NullString { return sql.NullString{String: s, Valid: true} }
```

Rules:

- The function must have the signature `func(X) W` where `W` is assignable to the field type.
- The generator is validated against `X`, not against the field type.
- A generic function (`optional.Some[T]`) is instantiated with the type arguments of the field type
  (`Option[string]` → `T = string`) before checking.
- An unqualified name refers to a function in the package the factory is generated into.
- A qualified function's package must be loaded: a package of the policy file (its types and
  qualified wrap functions are loaded), a package of PACKAGES, or a package they import.
- The field is not decomposed into pointers or slices: the function builds the whole field.
  Wrapper types are often slices themselves (go-optional's `Option[T]` is `[]T`).
  Hence `count` cannot be combined with `wrap`.
- Generic functions are called with explicit type arguments (`null[string](...)`).

datlas stays unaware of go-optional, sqletch and sqlc.

`wrap=` is independent of external policies and is also available in struct tags.

# Coexistence with Hand-written Factory Methods

## Hand-written methods

The generated `Factory` lives in the user's own package,
so methods can be added to it by hand in the same package, without any external policy.
No annotation is written anywhere; the generated struct is only used as a Go type:

```go
// fixture/insert_user.go
func (f *Factory) InsertUserParams(opts ...func(*gen.InsertUserParams)) gen.InsertUserParams {
	g := f.Faker()
	v := gen.InsertUserParams{
		ID:        g.UUID(),
		Email:     g.Email(),
		Bio:       optional.Some(g.Sentence()),
		CreatedAt: g.Now(),
	}
	for _, opt := range opts {
		opt(&v)
	}
	return v
}
```

The seed, the clock and unique values are shared with generated methods through `Faker()`.
Wrapper types need no `wrap=`: the constructor is called directly.

## Skeleton-only generation

### Problem

Hand-written methods need a generated `Factory`.
Today `Factory` is generated only when at least one `//datlas:fixture` type is found;
otherwise generation fails with `no //datlas:fixture types found`.

When every target type is generated by another tool (e.g. all models come from sqletch),
there is no `Factory` for hand-written methods to attach to.

### Alternatives

| Alternative | Assessment |
| --- | --- |
| Use `fixturekit` directly with a hand-written `Factory` holding `*fixturekit.Generator` | Works today, with the same capabilities. Moving to generated code later conflicts with the hand-written `Factory` and requires rewriting. |
| **Generate a skeleton `Factory` without any fixture type** (chosen) | Hand-written methods attach to the generated `Factory` from the start. Moving a type to the external policy later only means registering the same name and deleting the method. |

### Rule

The skeleton contains `Option`, `WithSeed`, `WithClock`, `WithNow`, `WithTimePrecision`, `WithT`,
`Factory`, `New`, `Seed` and `Faker`: everything generated today except the per-type methods.

Simply dropping the error would hide mistaken package patterns. Instead:

- `datlas fixture` without PACKAGES and without `-config` explicitly generates the skeleton only
- PACKAGES given but no `//datlas:fixture` type found (and no `-config` entry) remains an error

```go
// fixture/doc.go
package fixture

//go:generate go run github.com/moznion/go-datlas/cmd/datlas fixture
```

## Mixing both

Both kinds of methods are methods of the same `Factory`, so the choice is made per type:

```
fixture/
    doc.go              // go:generate
    fixture.yaml        // types with many, frequently changing fields
    zz_fixture_gen.go   // f.User(), f.Users(n)
    company.go          // hand-written: f.Company()
    scenario.go         // hand-written, built on generated methods
```

Hand-written methods may call generated ones:

```go
func (f *Factory) AdminUser() gen.InsertUserParams {
	return f.User(func(u *gen.InsertUserParams) { u.Role = "admin" })
}
```

| | External policy | Hand-written |
| --- | --- | --- |
| Boilerplate | none | one method per type |
| Removed field | generation error | compile error |
| Added field | generation error | **not detected** |
| Wrapper types | `wrap=` | direct constructor call |
| Plural method (`Users(n)`) | generated | written by hand if needed |
| Arbitrary construction logic | no | yes |

Recommended use: start hand-written, and move a type to the external policy
when its fields become numerous or change often.

## Name conflicts

A hand-written method and a generated one with the same name only fail at `go build`,
as a duplicate method declaration.
datlas detects this at generation time instead.

The names of the methods of `Factory` declared in the output package,
excluding `zz_fixture_gen.go`, are reserved, in addition to `Faker` and `Seed`.
Both singular and plural factory method names are checked against them.

The names are collected from the AST, not from type information:
the loader replaces the previously generated file with an empty one,
so `Factory` itself is undefined while loading and its methods cannot be resolved as types.

## Migrating a type

To move a type from a hand-written method to the external policy:

1. add an entry with the same `name` to the policy file
2. delete the hand-written method

Forgetting step 2 is reported by the conflict check.
Callers keep working unchanged because the method name and signature stay the same.

## Nested fixture types

Generated code calls the factory of a nested fixture type automatically (e.g. `Company: f.Company()`).
This applies only to types datlas generates factories for; hand-written methods are never called automatically.

# Internal Changes

## analyze

`analyze` currently reads tags directly:

```go
tag, ok := reflect.StructTag(d.Struct.Tag(i)).Lookup(TagKey)
```

This lookup becomes a per-source function returning the policy string of a field.
Directive-based and config-based sources then produce the same `FixtureType`,
and the renderer needs no change for them.

```
//datlas:fixture ──▶ tag lookup    ──┐
                                     ├──▶ analyze ──▶ FixtureType ──▶ render
fixture.yaml     ──▶ config lookup ──┘
```

The set of reserved names is extended with the `Factory` methods declared by hand
in the output package (see [Name conflicts](#name-conflicts)).

## Generate

When neither PACKAGES nor `-config` is given, package loading and analysis are skipped
and the renderer is called with no fixture types.
The zero-type error remains for the case where PACKAGES are given.

## loader

The package paths referenced by the config are added to the loaded patterns.
So is the output package, so that its wrap functions share their types with the fields
(types of separate loads are never identical).
`loader.PackagePaths` lists the packages matched by PACKAGES alone, which are scanned for directives.

The non-generated files of the output package are parsed to collect `Factory` method names.
The output package may not exist yet; then no names are reserved.

## render

Imports of the packages of `wrap` functions are added.

# Relationship to DESIGN.md

The design principles stay intact:

1. Go structs remain the single source of type information.
   The policy file references types; it never defines them.
2. The generator still produces only typed Go code and never touches a database.

---

# Implementation Order

1. Skeleton-only generation (makes hand-written methods usable for generated types on its own)
2. Reserve hand-written `Factory` method names (useful on its own, even without external policies)
3. Refactor `analyze` to take a tag lookup function
4. `-config` loading, validation and the explicit-field rule
5. `wrap=`
6. README section and an example using generated types, covering hand-written methods
